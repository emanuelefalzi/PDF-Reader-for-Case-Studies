# Fake `claude` CLI

Imitates the behavior of the real Claude Code CLI as observed in the initial
spike and used by the app (SPEC §4, §7.5, §7.8). The whole test suite uses it
in place of the real CLI; real calls only happen with `LELEPDF_REAL_CLAUDE=1`
(SPEC §10.2).

## Imitated commands

- `claude --version` -> `2.1.268 (Claude Code)`
- `claude --help` -> list of flags (SPEC §13): `ClaudeCLILocator` queries it
  once and checks that `--json-schema`, `--safe-mode`, `--strict-mcp-config`,
  `--input-format`, `--include-partial-messages`, `--system-prompt` and
  `--no-session-persistence` all appear.
- `claude auth status` -> JSON `{loggedIn, authMethod, email, subscriptionType}`
- `claude -p <prompt> … --output-format json` -> a single JSON `result`
  object with `structured_output` (analysis of a block, or contents if the
  schema passed with `--json-schema` contains `"entries"`).
- `claude -p --input-format stream-json --output-format stream-json …` ->
  persistent process: reads JSON lines from stdin (`{"type":"user",...}`) and
  writes `system`/`stream_event`/`assistant`/`rate_limit_event`/`result`
  events until stdin is closed.

## Modes (`FAKE_CLAUDE_MODE`)

| Value | Behavior |
|---|---|
| `success` (default) | Valid response; for the chat, identical to `chat_stream` |
| `chat_stream` | Alias of `success`, meant for chat use |
| `invalid_json` | The one-shot command prints text that is not valid JSON |
| `timeout` | The process sleeps forever until it is terminated |
| `not_logged_in` | Error message on stderr and exit 1 (also `auth status`) |
| `rate_limit` | `result` with `is_error: true` and the message `"Claude AI usage limit reached|<epoch>"`; in chat a `rate_limit_event` in the real nested format is also emitted (`rate_limit_info.status: "rejected"`) |
| `rate_limit_warning` | Chat only: successful turn, but a `rate_limit_event` with `rate_limit_info.status: "allowed"` and usage at 85% (warning threshold) |
| `rate_limit_legacy` | Chat only: like `rate_limit`, but the `rate_limit_event` uses the old format with the keys at the root instead of `rate_limit_info` (checks backward compatibility) |
| `network` | "getaddrinfo ENOTFOUND"-style message on stderr and exit 1 (`ClaudeErrorMapper.isNetwork`) |

Since v2.1.26x the real CLI sends a `rate_limit_event` on EVERY chat turn (not
only when the limit is hit), almost always with `status: "allowed"` and low
usage: the modes above that do not explicitly deal with the limit (e.g.
`success`) now also emit an "allowed" `rate_limit_event` at 27%/37% before the
`result`, to mirror this behavior.

## Environment variables

- `FAKE_CLAUDE_MODE`: see the table above.
- `FAKE_CLAUDE_MODE_FILE`: path of a file with one mode per line. Each
  invocation consumes (and removes from the file) the first non-empty line; if
  the file is empty or missing, it falls back to `FAKE_CLAUDE_MODE`. It serves
  the tests that need several consecutive calls to behave differently, for
  example `invalid_json` followed by `success` for the automatic retry of
  `BatchRunner` (SPEC §7.5).
- `FAKE_CLAUDE_RESPONSE_FILE`: path of a file with the response to print
  instead of the one generated by default (either the `structured_output` or
  the whole `result` envelope, detected automatically from the content).
- `FAKE_CLAUDE_FIXTURES_DIR`: replay folder. For every call the sha256 of the
  prompt text is computed (the argument of `-p`, or the user text for the
  chat) and if `<dir>/<sha>.json` exists its content is used as the response.
  It takes priority over `FAKE_CLAUDE_RESPONSE_FILE`.
- `FAKE_CLAUDE_LOG`: path of a log file; every invocation appends a JSON line
  with `argv`, `mode`, `cwd` (the working directory of the process,
  `os.getcwd()`) and a timestamp. Useful for the tests that must verify the
  flags and the working directory passed by the app.

## Notes

- The argument parser is deliberately simple: it only recognizes the flags
  needed to decide the response (`--model`, `--effort`, `--system-prompt`,
  `--json-schema`, `--input-format`, `--output-format`, `--tools`,
  `--permission-mode`); the others are ignored.
- The successful analysis response takes, when possible, the words of the
  marks directly from the prompt text (§7.5): two marks for each of the 4
  types (rectangle, circle, underline, arrow).
- The successful contents response (schema with `"entries"`) reads the real
  candidates from the prompt text written by `TocGenerator.buildPrompt` (lines
  `"- p.N [suggested level L, ...]: \"Title\" — followed by: ..."`) and returns
  those titles/pages/levels as they are, instead of a fixed contents list:
  useful to verify that the app really builds the prompt with the candidates
  of the pipeline. If it finds no recognizable lines it falls back to a fixed
  sample contents list with 3 entries.
- In the chat, the default reply text deliberately contains the markers
  `[p. 3]` and `<fuori>…</fuori>` split in the middle between two chunks, to
  exercise the app's streaming parser (SPEC §7.8).
- The canned sample texts (analysis title, rewrite words, chat reply,
  fallback marks) are in Italian on purpose: some tests match on them.
